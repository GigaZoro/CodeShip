# Interface translation

Every client string goes through [`@t3tools/shared/i18n`](../../packages/shared/src/i18n.ts).
A message is its English source text, so English needs no catalog and a message missing from a
catalog renders in English. Catalogs live in
[`client-runtime/src/i18n/locales`](../../packages/client-runtime/src/i18n/locales) and load on
demand, so an English session never downloads one.

## Writing UI text

- `t("Archive thread")`, `t("Delete {name}?", { name })`, and `tn(count, "{count} file", "{count} files")`
  for anything count-dependent: Ukrainian has three plural forms.
- `tx` (web and mobile `i18n` modules) fills placeholders with elements, so a sentence with a
  link or `Kbd` inside stays one message. Never translate fragments and concatenate them.
- `t` only accepts a string literal or a `Message` from `msg()`. That is how the extractor sees
  every message: a plain `string` is a type error. Module-level tables hold `msg("...")` and
  translate where they render.
- Never call `t` at module scope. Desktop and mobile choose the language after modules load.
- Text that leaves the client stays English: prompts, commit and PR text, MCP tool text, logs.
  Server and provider strings are data and are shown as received.
- `t3code/no-untranslated-text` flags raw JSX text and text props, copy in object fields such as
  toast titles and option labels, and text passed to alerts and announcements. Text that stays
  as written goes in a JSX expression (`{"GitHub"}`); anything else that isn't copy (stored
  defaults, text sent away) gets a suppression that says why.
- The development pseudo-language (Settings → General → Language → Pseudo, dev builds only)
  brackets and stretches every translated string, so leftover English and clipped layouts stand
  out.

## Catalogs

`node scripts/i18n-catalog.ts check` (CI and `check:changed` run it) fails on messages missing
from a catalog, stale entries, mismatched placeholders, missing plural forms, and translations
left identical to the English unless every word is on the glossary's keep list. The
[translate-ui](../../.agents/skills/translate-ui/SKILL.md) skill fills catalogs with the shared
glossary, and [upstream-sync](../../.agents/skills/upstream-sync/SKILL.md) brings upstream's plain
English text into this model after a merge.

To add a language: add its code to `APP_LANGUAGES` with its native name, a loader in
[`catalogs.ts`](../../packages/client-runtime/src/i18n/catalogs.ts), a catalog file, and an entry
in the script's `CATALOGS`.

## Applying a language

The choice is per device: `ClientSettings.language` on web and desktop, mobile preferences on
mobile. "system" resolves against the OS or browser languages. Dates and numbers use
`getFormattingLocale()`, which keeps the system's regional format when its language matches.

Nothing re-renders when the language changes; each surface restarts its UI instead.

- Web loads the catalog in [`languageBoot.ts`](../../apps/web/src/languageBoot.ts) before the app's
  modules, and reloads the page after a change. Desktop renderers read the saved choice through a
  sync IPC, because the packaged app pins `navigator.language` to en-US.
- The desktop main process activates the language before building its menu and rebuilds the menu
  when the setting changes.
- Mobile holds the splash until the language is active, then remounts the navigator with its
  current state after a change.
