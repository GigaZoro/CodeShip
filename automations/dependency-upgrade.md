## T3.CodeShip's facts for the skill

- **Manifests.** The root `package.json` (`packageManager`, `engines.node`, its dependencies), the `package.json` of every workspace package (`apps/*`, `packages/*`, `infra/*`, `evals`, `scripts`, `oxlint-plugin-t3code`), and `pnpm-workspace.yaml`: `catalog`, `overrides`, `patchedDependencies` with `patches/`, `allowBuilds` and `minimumReleaseAgeExclude`. Also `native/*/Cargo.toml` with their `Cargo.lock`, every `uses:` in `.github/workflows/*.yml` and `.github/actions/*/action.yml`, and the tool versions passed to setup actions. Find what is outdated with `pnpm outdated -r --format json` and `pnpm audit --json` from the worktree root.
- **Node and pnpm.** `engines.node` in the root `package.json` is the development Node pin, and every workspace that declares `devEngines.runtime` (today `apps/server`) repeats it: `.github/scripts/check-node-runtime.cjs` fails unless they match, so they move together. When the pin moves, install that Node on this machine the way `~/.agents/rules/machines.md` "Missing tools" says before running any check, confirm `node --version`, and update every doc that names the version. `packageManager` moves pnpm. The `engines` range of the published server package `t3` is the Node versions users can run it on: a compatibility promise, not a pin, so this run never raises it. `@types/node` (a catalog entry) keeps the major it has.
- **Aliases and families.** `typescript` is an alias of `@tsc-rs/typescript` and `vite` of `@voidzero-dev/vite-plus-core`: upgrade the alias target, keep the alias. `vite-plus` and its core move together, as do the Effect packages and the alchemy packages. A bump of Effect or alchemy also runs `vpr sync:repos` so `.repos/` matches it; never edit `.repos/` by hand and never upgrade anything inside it.
- **Prerelease channels.** alchemy, `@distilled.cloud` and `node-pty` are tracked on prerelease channels on purpose: they follow the skill's prerelease-channel rule.
- **Release age.** pnpm's own default age is shorter than the skill's 3 days, so every install that resolves new versions is `vp i --ignore-scripts -- --config.minimum-release-age=4320` (the skill's step 3.3), and `vp add` gets the same two flags. `minimumReleaseAgeExclude` skips pnpm's check for its entries (`@tsc-rs/*` for every version): check each of those packages' publish dates against the cutoff yourself. When a package moves past a version named there, delete that entry. Add an entry only for a vulnerability fix younger than the cutoff, with a comment naming the advisory.
- **Patches.** Every package in `patchedDependencies` is pinned in `overrides` too, so release installs cannot drift past the patch. Move the patch and its pin together, as the skill's "Port local patches" says.
- **Install scripts.** `allowBuilds` lists the packages whose install scripts run (`esbuild`, `node-pty`, `sharp`, `@tsc-rs/typescript` among them): a changed version of each is read as the skill's step 3.4 says before `pnpm rebuild` runs it. A package new to the lockfile that wants to run install scripts gets an entry: `false` unless it does not work without its script, and `true` only after you read the script and the review names it.
- **Desktop.** After an Electron bump, run `vp run --filter @t3tools/desktop ensure:electron` before anything that loads it.
- **Mobile.** This run upgrades the JavaScript-only dependencies of `apps/mobile`. The Expo SDK, `react-native`, `react` as `apps/mobile` resolves it, and every mobile dependency with native code (an `ios/` or `android/` directory, a `.podspec` or an `expo-module.config.json` in the package) come from upstream through the weekly sync: no machine here can build the iOS app, CI checks native sources only with linters, and the two tarballs in `apps/mobile/deps` are forks upstream builds against its own React Native (`apps/mobile/deps/README.md`, `docs/operations/mobile-screens-fork.md`). This is the project's policy pin for those packages: they are not holds and need no item. A catalog entry that `apps/mobile` shares stays inside the Expo SDK's range, and `npx expo install --check` in `apps/mobile` passes after every batch.
- **Rust.** Compare each direct dependency of `native/*/Cargo.toml` with crates.io as the skill's inventory says and raise the requirement for a new major or a new `0.x` minor; then `cargo update --manifest-path native/<crate>/Cargo.toml`. Check each crate as CI's Rust job does: `cargo fmt --manifest-path native/<crate>/Cargo.toml -- --check` and `cargo test --locked --manifest-path native/<crate>/Cargo.toml`. Without `cargo` on this machine, install the stable toolchain as "Missing tools" allows; when it may not, leave the crates for next week's run and say so in the report.
- **GitHub Actions.** `ci.yml` pins actions by major tag (`actions/checkout@v6`); `release-desktop.yml` and the composite actions in `.github/actions/` pin by commit SHA with the version in a comment. Each reference keeps its form, as the skill's CI rule says, and a SHA is checked against its release tag before it is written. The release workflow runs only on a push to `main`, so review each change to it as a change to what signs and publishes a release.

## Checks

Run each check with `t3_command_run`, from the worktree, with `CHECK_CHANGED_TIMEOUT=3600` in its environment:

1. `vp run check:changed --suites <dir> [--suites <dir>...]` for every workspace package whose resolved dependencies changed and that has a `test` script (`--suites` refuses a package without one). A change to the root `package.json`, a `catalog` entry or an `overrides` entry changes every package that uses it, so list each of them. If browser tests cannot start because Playwright's Chromium is missing, install it the way `.github/workflows/ci.yml` does and rerun: tests that never ran do not count as passing.
2. `vp run --filter @t3tools/desktop ensure:electron`, then `vp run build:desktop`, the build CI's "Build and Typecheck" job runs, and `vp run build` for every other app.
3. The Rust checks above for each crate whose dependencies changed.
4. Last, on the final tree, `vp run check:changed` without `--suites`: the typecheck, lint and tests of the changed files, which is also the pass the push gate looks for.

A test that fails: rerun its file alone. If it passes alone twice, it is a load flake; note it in the report. Otherwise fix its root cause on the branch. When it fails on `main` too, run it in a temporary detached worktree of the base to prove that, and file it as a follow-up (below) unless the upgrade is what broke it.

## Review and landing

- **Release notes** are part of the skill's "Record" step, committed before the review: prepend one dated entry to `docs/release-notes.md` as `docs/operations/release.md` "Release notes for every shipment" describes: `## YYYY-MM-DD — Library updates`, then up to 5 bullets in the product's voice on what users notice (a new Electron and Chromium, a new Node for the bundled server, fixes the release notes of an upgraded library name), or the one bullet "Keeps T3.CodeShip's libraries up to date; nothing changes in how it works." when nothing shows.
- **Review.** Review each batch commit yourself, then get the independent review: a fresh `delegate_task` with role `review` on the other provider's primary reviewer as this session's auto-mode instructions name it (without them, the strongest model `orchestrator_capabilities` lists for that provider, at its highest effort), with a `clientRequestId`. Give it the exact commit, the diff without the lockfiles (`git diff origin/main...HEAD -- . ':(exclude)pnpm-lock.yaml' ':(exclude,glob)native/*/Cargo.lock'`) and the list of resolved package changes in them. When it cannot run, the run does not land: push the branch and file the follow-up.
- **Landing.** Land with the `ship` skill; leave `~/Projects/CodeShip` as it is and skip the ship skill's fast-forward of that checkout. When it rebases, resolve conflicts as the skill's "Land" step says (lockfile: `origin/main`'s, then the install from "Release age") and compare `git range-diff` before its push: a changed diff goes back to the checks and both reviewers. After the push, follow CI's run for that commit on `main` (`gh run list --branch main --commit <sha>`, then `gh run watch <id> --exit-status` with `t3_command_run`); a failure caused by the upgrade is fixed forward or reverted as the skill says. When the push cannot land after its root cause is fixed, push the branch, remove the worktree, and file the follow-up naming the branch and its last commit.

## Holds and follow-ups

- A hold, a run that could not land and a test that fails on `main` too are each a CodeShip follow-up in Azure DevOps (`~/.agents/rules/work-items.md`, "CodeShip follow-ups"): `node ~/.agents/tools/long-term-fix.mjs file --project codeship --follow-up --title "<title>" --body <file> --criteria "<the check that proves it>"`, first without `--apply` to read `similar.open` (extend an open item instead of filing a second), then with `--apply`.
- A hold is filed with `--tags "Dependency-Hold"` as well, in that same call, so the Machine inbox never starts a chat on it: it waits for a release outside this repository. Its title is the skill's `Dependency hold: <package> <held> (newest <version>)`, its body names the blocker (the error, or the upstream issue URL) and its criteria the upgrade passing these checks. Where the held version lives in `pnpm-workspace.yaml`, add a one-line comment beside it naming `AB#<id>`. Every run retries every open hold first: `long-term-fix.mjs holds --project codeship` lists them all. Close a lifted one once its commit is on `main`: `long-term-fix.mjs set <id> Closed --comment "<commit and checks>"`.
- Every other follow-up stays New for the Machine inbox, which starts a CodeShip chat on it two hours after it was filed. This run launches no chats.
